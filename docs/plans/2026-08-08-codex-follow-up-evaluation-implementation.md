# CodexReach 通用后续评估系统实施计划

日期：2026-08-08
依赖设计：`docs/plans/2026-08-08-codex-follow-up-evaluation-design.md`

## 1. 实施原则

- 先打通人工数据的完整闭环，再接 GSC 和 Cloudflare。
- 新模块通过事件接口接入现有 CodexReach，不把评估业务塞入回合 Hook、飞书消息处理或 Codex client。
- 每阶段均可独立上线、关闭和回滚。
- 数据迁移必须可重复运行；外部写操作必须幂等。
- 默认使用功能开关 `EVALUATION_SYSTEM_ENABLED=false`，完成试点后再开启。

## 2. 阶段 0：基础约束与接口

### 任务

1. 定义 `ActionCandidate`、`ActionBatch`、`Deployment`、`EvaluationPlan`、`EvaluationNode`、`EvaluationRun`、`BaselineSnapshot` 等类型。
2. 定义领域事件：`TurnCompleted`、`CandidateDetected`、`DeploymentVerified`、`DraftConfirmed`、`EvaluationDue`、`EvaluationStarted`、`EvaluationFinished`。
3. 增加评估模块配置、功能开关、时间与 ID 注入接口，保证测试可控。
4. 明确现有 project/session/topic 映射接口，避免评估模块直接读取内部状态文件。

### 验收

- 类型检查通过。
- 领域模块不依赖具体飞书、GSC 或 Cloudflare SDK。
- 功能关闭时现有行为和测试不变。

## 3. 阶段 1：SQLite 与核心状态机

### 任务

1. 为候选、批次、行动、部署、计划、节点、运行、快照、集成、话题绑定和 outbox 建表。
2. 增加唯一索引、外键和状态迁移约束。
3. 实现 repository、事务封装、迁移版本和补偿扫描。
4. 实现候选 30 天陈旧、90 天过期规则。
5. 实现初始草稿第 1/3 天提醒、第 7 天归档；到期确认第 1/3/7 天提醒。

### 测试

- 重复事件幂等。
- 并发点击只创建一次运行。
- 服务在各状态重启后能继续。
- 错过多个提醒只补发当前阶段。
- 非法状态跳转被拒绝。

## 4. 阶段 2：行动识别与批次

### 任务

1. 从回合完成事件收集用户意图、结果、项目、Git、文件、commit 和部署线索。
2. 实现规则预筛选，排除查询、解释、构建失败和未采用草稿。
3. 实现固定 JSON schema 的模型分类器，验证和拒绝非结构化结果。
4. 实现相同项目、连续 commit、范围重叠的候选合并。
5. 实现以部署/真实操作为批次边界以及拆分、合并数据结构。

### 测试

- 代码修改未部署时不产生飞书消息。
- 连续修改合并为一个候选。
- 不相关文件或不同项目不合并。
- 构建失败、取消和回滚正确终止候选。
- 分类器失败时安全降级，不创建任务。

## 5. 阶段 3：飞书草稿、统一任务清单与到期闭环

### 任务

1. 初始化并复用 `Codex 后续评估` 清单及必要分组。
2. 获取并保存当前用户 `open_id` 作为默认负责人。
3. 实现草稿卡片：确认、调整、拆分/合并、无需评估。
4. 实现原 Session 话题路由；缺失时按需创建并绑定“部署与评估”话题。
5. 确认后创建评估节点和飞书任务，保存 GUID、链接与同步版本。
6. 实现调度器、到期卡片、延期、取消、人工完成和异常处理。
7. 用户确认开始后创建新的评估话题与 Codex Session，注入结构化提示。
8. 实现 outbox 重试和飞书写操作幂等。

### 测试

- 重复确认不创建重复任务。
- 多 Session 部署正确路由到固定话题。
- 固定话题只创建一次。
- 修改截止时间可同步。
- 第 1/3/7 天提醒准确。
- 任务完成、删除、延期和 Codex 执行失败均有确定状态。

### 阶段验收

使用人工评估数据完成一次从候选、部署确认、任务到期、启动新 Session、结果回写到任务完成的全链路。

## 6. 阶段 4：飞书 Base 台账

### 任务

1. 在现有 Base 新增 `行动记录`、`评估计划`、`评估结果`，建立与 `项目清单` 的关联字段。
2. 为 `项目清单` 增加待确认、待评估、逾期、最近结论和下一评估时间等聚合字段。
3. 实现确认后写入、任务创建后回写、运行完成后新增结果。
4. 实现本地 ID 与 Base record ID 映射、失败重试和人工修正保护。
5. 提供只读对账命令，报告本地与 Base 的缺失、重复和状态差异。

### 测试

- 草稿未确认前 Base 无正式记录。
- 结果永远新增而不是覆盖历史。
- Base 暂时不可用不阻塞本地调度。
- 重试不会重复新增记录。

## 7. 阶段 5：页面检查与 SEO 模板

### 任务

1. 实现 SEO 行动识别：metadata、canonical、结构化数据、内链、URL、sitemap、robots 和重定向。
2. 实现页面快照：状态码、重定向、主要标签、robots、结构化数据摘要、资源版本和内容指纹。
3. 实现精确 URL、URL 前缀、页面集合和全站范围选择。
4. 实现 SEO 默认节点：立即、7 天、28 天和可选 60 天。
5. 实现后续变更冲突检测与“无法归因”提示。

### 测试

- 动态页面不会仅因无关 HTML 变化误判部署。
- metadata 等预期字段可精确验证。
- 新页面与已有页面使用不同的评估逻辑。
- 观察期内重叠改动会被标记。

## 8. 阶段 6：Google Search Console

### 任务

1. 增加 OAuth 连接、回调、刷新、撤销和状态页面，申请最小只读权限。
2. 将 refresh credential 保存到 macOS Keychain，日志全链路脱敏。
3. 获取可访问资源并让用户确认项目映射。
4. 实现按资源、页面、查询词和日期窗口查询指标。
5. 实现修改前 28 天、再前 28 天和修改后完整窗口快照。
6. 实现缓存、API 限制、数据延迟、空数据和权限异常处理。
7. 输出结构化 SEO 结论和置信度，不宣称严格因果。

### 测试

- OAuth 凭据不出现在数据库明文字段、日志、飞书和 Codex 提示中。
- Token 过期可刷新，撤销后状态正确。
- 不完整窗口不会用于正式结论。
- 原始快照不可覆盖，修正会生成新版本。

## 9. 阶段 7：Cloudflare 部署发现

### 任务

1. 增加最小只读 API Token 连接与权限测试，凭据保存到 Keychain。
2. 自动发现并人工确认 Pages/Workers、生产分支和域名映射。
3. 查询最新生产部署、部署 ID、时间、版本和可用 commit。
4. 实现候选 commit 范围与生产部署匹配。
5. API 不可用或 Worker 无 commit 时使用网页指纹降级。
6. 有候选项目每 10～15 分钟扫描；验证中每 2～5 分钟；失败指数退避。
7. 区分 `deployed_at`、`verified_at`、`effective_at`，以线上验证时间启动观察窗口。

### 测试

- 外部部署能激活正确候选。
- 无候选的普通部署不打扰用户。
- 相同 deployment ID 不重复生成批次。
- CDN 仍为旧内容时不提前计时。
- API 权限丢失时降级并只提示一次。

## 10. 阶段 8：管理、可观测性与试点

### 任务

1. 管理页展示功能开关、集成状态、项目映射、待确认、逾期、异常和重试队列。
2. 增加脱敏结构化日志、核心计数和诊断命令。
3. 为异常队列提供重试、取消、重新绑定与重建任务入口。
4. 在 `classgames.net` 单项目开启试点，其他项目保持关闭。
5. 记录识别准确率、草稿确认率、重复率、到期执行率和错误率。
6. 试点稳定后按项目逐步开启。

### 建议上线门槛

- 重复任务率为 0。
- 错误项目/话题路由为 0。
- 凭据泄漏检查为 0。
- 端到端主路径测试全部通过。
- 服务重启与飞书/Google/Cloudflare 短暂故障后可自动恢复。

├── outbox.ts
├── templates/
│   ├── seo.ts

现有 `src/feishu.ts`、`src/codex-client.ts` 和回合 Hook 只暴露必要接口与事件，不承载评估状态机。

## 12. 推荐执行顺序与里程碑

1. **M1：核心状态机**——阶段 0～2。
2. **M2：人工闭环可用**——阶段 3～4。
3. **M3：SEO 自动评估可用**——阶段 5～6。
4. **M4：外部部署自动识别**——阶段 7。
5. **M5：单项目稳定上线**——阶段 8。

每个里程碑完成后运行类型检查、单元测试、集成测试，并进行一次真实飞书端到端验证；在 M2 之前不启用任何真实自动任务创建。
